# Joint review: the interface, its patterns, and whether it is usable

**Date**: 2026-11-16 · **Asked by**: the owner, after the `caravan init` mock-up · **Reviewers**: a data
scientist (time-series and sensor ML for embedded targets), a CLI/TUI UX designer, and an embedded
firmware developer (Cortex-M, ESP32, TFLM, CMSIS-NN). Each reviewed alone first, then read the other
two reports and answered them. This note is the synthesis; the round-1 and round-2 reports are
summarised in the appendix.

Scope: the whole interface a user meets — the manifest, the CLI, the export as the firmware's
interface, the documentation — and the planned `caravan init` as shown in the mock-up of
2026-11-16.

---

## 1. The joint verdict

The engineering is careful and in places better than comparable tools: preprocessing fitted on the
training split only and built into the model, a three-way int8 gate with per-layer error tables,
every dropped window counted, binding by name from the model's own signature, a resolver with exactly
the model's operators, and test windows that let a board check its answers against the host's bit for
bit. The exit codes, the "no option skips a gate" rule and `render`'s derived values are good
interface design.

The interface rests on two foundations that are not yet sound, and the wizard as designed would make
both look more trustworthy than they are:

1. **The data model** — how rows become training examples — is too narrow for the application
   classes the documentation claims. It silently produces zero examples for a continuous target,
   drops rare-event classes, joins separate recordings, and defaults to a split that leaks between
   neighbouring windows.
2. **The memory model** compares lower bounds against whole-chip figures no firmware ever gets, so a
   pass looks much safer than it is.

The third weakness is the everyday loop: `validate` reports one phase at a time, `--json` and rule
IDs do not keep what the docs promise, and the first command that needs the training extra prints an
install command that cannot work.

**All three agree: fix the data model and the memory model before `init` ships, put the wizard's
analysis into the core so it is not trapped in a one-time session, and then build `init` as a front
end over it.**

## 3. The tensions, and how they resolve

**3.1 Wizard, editor schema, or analysis command?** All three: *both, layered.* Order:
(1) a JSON Schema with a `# yaml-language-server: $schema=…` line, for everyone who edits the file by
hand; (2) one analysis engine in the core — column profile, window table with per-split counts and
durations, memory budget, MACs — available without prompts and as JSON; (3) `init` as a front end over
that engine. *Open for the owner:* whether (2) is a new verb (`caravan plan` / `caravan inspect`,
needs an amendment of Principle XII) or lives in existing ones (`render` on a manifest, `init --plan`
on data). The reviewers split on this; the UX designer prefers no new verb.

**3.2 Full-screen TUI or line prompts?** The owner chose a full-screen TUI as an optional extra; the
reviewers accept it on two conditions: the question engine lives in the core, so line mode and
`--no-input` keep working without a terminal (which amendment v4.3.0 requires), and the extra gets an
explicit amendment — Principle XII names its four extra slots by pipeline stage, and an authoring
extra fits none of them. Using the unbuilt benchmarking slot quietly is ruled out.

**3.3 Where does the window proposal come from?** Both sources, in different roles. With a sample
period, ask how long the phenomenon lasts in seconds and convert to rows — that is the physics. Label
run lengths and *per-split* counts then check feasibility and warn. Without a sample period, fall back
to run lengths and say it is a data-availability guess. The mock-up's "training examples per class"
counted all three splits; show test windows per class, because they decide how finely the gate can
measure.

**3.4 Training with overlap?** Yes, but only behind the group split. Leakage comes from the split,
not from overlap; with per-recording windows and a group split, a training stride below the window is
safe, standard augmentation, and makes the model robust to the mid-event offsets a streaming device
feeds it. `training_stride` defaults to the window and is only allowed smaller with a group split.

**3.5 Which quantization choices?** `int8` (default, accelerated) and `none` (float32, for
comparison). Remove `float16`. Add `int16x8` later as the fallback when the int8 gate fails, after
per-operator support is verified. The UX designer would hide `none` from the wizard; the other two
would keep it labelled "for comparison". The question stays, as the owner asked.

**3.6 How many questions?** The fixes add questions; the UX designer's rule resolves it: *ask only
when the data makes the answer matter, and otherwise propose it on the review screen with its reason.*
Ten questions always (data, board, quantization, output, its kind, inputs, window, template, its
parameters, budget — name and file become review-screen proposals), up to three when the data calls
for them (window label rule when labels change inside the proposed window or the output is a
continuous number; split when it is consequential; a board of one's own).

**3.7 "My own board".** Everyone wants it; adding a board today means editing the installed package
(`targets/registry.py:52-56`). It needs a project board directory or search path first. Whether
`init` may *write* that board file is open: amendment v4.3.0 lets `init` write one manifest and
nothing else. Until that is decided, the option points to the how-to.

**3.8 The memory panel.** Replace the "≥ x %" bars with a stacked budget per board, sketched by the
firmware developer:

```
s32k144  usable RAM 56 KB (largest block 28 KB) · app flash 480 KB   [board file: NXP RM]
 RAM   runtime+stack ~6 KB  ████
       arena  ≥ 9 KB … ~14 KB  ███████░░░       est. (floor … planner)
       your firmware (reserve) 20 KB  ··········
       left  ≥ 16 KB                             ✓ arena fits largest block
 flash runtime ~45 KB  ███   weights ≥ 18 KB  █   left ≥ 417 KB
 compute ~0.4 M MAC/inference · est. 6–15 ms @80 MHz (cmsis-nn) · stride 320 ms ✓
 estimated; measured after a board run
```

A ✗ only where a floor alone exceeds the usable figure or the largest contiguous block. The reserve is
a default the user edits on the review screen. (The figures are illustrative; the s32k144 split is to
be checked against the reference manual.)

## 4. The joint proposal, in order

Each package is a feature of its own; the order is the dependency order. "Done" is what all three
would accept.

**P1 — A data model that knows recordings** (data scientist's top item; first for all three).
Windows restart per file or `sequence_column`; `preprocessing.window_label: all_equal | last | mean |
any:<value>` (default `all_equal` for classes, `last` for numbers); `split: {type: group, by: file |
<column>}`; `training_stride` (≤ window, smaller only with a group split); windowed data never resolves
to `random` silently. *Done:* a continuous state-of-charge fixture yields windows, a fixture with
interleaved bursts keeps its rare class, two-file data is never joined into one window.

**P2 — An honest memory model.** Board schema gains `ram_usable_kb`, `largest_contiguous_ram_kb`,
`app_flash_kb` and runtime figures, each sourced; the fit check uses them; an arena estimate from a
greedy-planner replica (tensor lifetimes already exist in `export/memory.py`) plus overheads; MACs per
layer. *Done:* `build` and the reports show runtime / weights / arena range / reserve; the
VWW-96-on-s32k144 case is refused or flagged; every figure labelled `estimated`.

**P3 — The time and window contract.** `sample_period_ms` (or `event`) in the manifest; interface
contract gains `window_order`, `window_label`, `training_stride`, a recommended `inference_stride`,
`warmup_rows` and derived durations, mirrored as header constants. *Done:* the skeleton has a ring
buffer with warm-up and the recommended stride; the docs say how to smooth results.

**P4 — An edit loop that works, and the analysis in the core.** One-pass validation with
`file:line:col`, rule IDs and doc links; `--json` always a JSON document; the real install command in
exit-4 messages; `validate` writes no run directory by default; a JSON Schema with a modeline; the
analysis engine (profile with vocabulary coverage, window table per split with durations, memory
budget, MACs) as JSON, on a core-only install. *Done:* a file with four errors shows four findings in
one run; VS Code completes the manifest; CI gets the footprint without the training extra.

**P5 — `caravan init`, rebuilt on P1–P4.** The question engine in the core (line mode and
`--no-input`), the full-screen TUI as an extra after its amendment; 10 + up to 3 questions; no board
proposal; quantization `int8` / `none`; the split written explicitly; the repeat command with every
answer explicit; a `next:` hint that knows the installed extras. *Done:* the contract, the mock-up
and the tests agree.

**Alongside, independent and small:** evaluation users can trust (majority-class baseline;
macro-F1 or balanced accuracy when classes are skewed; the gate also on float/int8 agreement and the
worst per-class recall drop; refuse or flag when test resolution exceeds the budget; anomaly
false-positive rate with an interval; calibration samples drawn evenly across classes) and a firmware
hand-off that survives a real board (`export --into <dir>`, `runs/latest`, the run path on stdout, the
model digest in every header with a `static_assert`, skeletons per runtime with ESP-IDF's `app_main`
and the schema-version check, a measured `invoke_us` in every board run).

**Cheap, do now:** remove `float16`; fix the exit-4 install hint; mark the tutorial's "measured" arena
line as example output (`docs/intro/tutorial03.md:115`, against Principle IV); fix the landing page's
example manifest, which does not validate, and `rules.md:43` (four templates, not two); stop rendering
an empty `defaults: {}`.

## 5. Decisions for the owner

1. **Order.** Accept that P1–P4 come before `init` ships (the reviewers' unanimous advice), and that
   feature 013 is re-scoped to P5 on top of them.
2. **Amendments of Principle XII.** (a) an authoring extra for the TUI; (b) whether `init` may write a
   board file next to the manifest; (c) whether the analysis gets a verb of its own.
3. **The `defaults` section.** Principle I says there must be none; the schema and
   `docs/ref/manifest/defaults.md` have one. Amend or remove.
4. **Defaults that change meaning** (allowed before 1.0 under Principle IX, with a change note):
   `representative_samples` and `model.version` get defaults; windowed data gets a non-random split;
   `float16` disappears.
5. **Sliding inference as the documented norm.** The contract stops implying stride = window on the
   device.

---

## 6. Keep

Train-only fitting recorded in `preprocessing.json`; the three-way gate with per-layer error tables
and stated resolution; every dropped window counted; the int8-calibrated anomaly threshold;
preprocessing inside the model with raw values in; binding by name from the flatbuffer signature;
the resolver from the file's operators; `test_windows.h` with host scores and `max_diff_steps` (the
strongest part, on a par with X-CUBE-AI's on-target validation); per-board kernel coverage traceable
to sources; exit codes including 4; "no option skips a gate"; accepted lists and did-you-mean;
`render --stdout`; reference docs in the Does / Default / Change it / Extremes pattern; the generated
manifest (short, commented, left-out columns listed, no defaults copied); in the mock-up the proposals
with reasons, the window timeline, lower bounds with the peak layer named, the review screen with
warnings, and "nothing written" until confirmed; budget proposals labelled with their source; no
pre-training estimate of quantization loss.

## 7. Not verified in this repository

The reviewers marked these as inferred from vendor and runtime knowledge: the S32K144 SRAM split
(SRAM_L 32 KB + SRAM_U 28 KB), whether TFLM's DEQUANTIZE accepts float16, ESP-NN's gains on the
classic LX6 versus the ESP32-S3, ESP-IDF's default optimisation level for this build, and TFLM's
overhead sizes. Each needs a source before it becomes a board figure or a rule.

## Appendix: the reports in brief

**Data scientist, round 1.** Careful engineering, too narrow a data model (A1–A4); the wizard's
window proposal is driven by remaining counts rather than the phenomenon, and mislabels all-split
counts as training examples; the int8 gate judges aggregate accuracy on possibly tiny test sets (one
flip in 12 windows is 0.083 against a 0.02 budget); type heuristics need vocabulary coverage; class
imbalance is supported but not surfaced; the anomaly threshold is right but rests on few points.
Keep the template defaults and the level of parameter exposure; never estimate quantization loss
before training. **Round 2:** agrees with the IoT stride and time-base positions (overlap is safe
behind a group split; add streaming evaluation); keep the quantization question as int8 / none; one
split question, always written.

**UX designer, round 1.** Sound base, weak edit-validate loop (A12–A14); the "minimal" manifest needs
fields nobody would guess; `validate` fills `runs/` and says `valid` for a missing dataset; no path
from one command to the next and silent training; the TUI conflicts with the extras budget and the
mock-up drifted from the contract; the repeat command was not reproducible; docs examples that do not
validate. **Round 2:** the other reports reorder the priorities; ask conditionally, propose the rest on
the review screen; the TUI over a core question engine, with an amendment; JSON Schema first.

**Firmware developer, round 1.** The export is better than most and in places cleaner than Edge
Impulse's SDK; the memory model is misleading (A5, A6) and the wizard's bars invite false trust;
stride and time base missing from the contract (A7, A8); float16 should go (A9); the skeleton is not
target-correct; no latency anywhere; no board proposal (A10); boards should be addable per project;
board and kernel data drift from the build; the tutorial labels illustrative output "measured".
**Round 2:** one consistent v4 contract (sample period, window size, order, label rule, training and
inference stride, warm-up, durations); the memory panel sketched in 3.8; "my own board" as a user-stated
board file in the project.
