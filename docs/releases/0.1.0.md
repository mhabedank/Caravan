# Caravan 0.1.0

The first release: a declarative pipeline from one YAML manifest to an int8 model, its C array and
its interface contract, for microcontrollers. Candidates are tagged `v0.1.0rcN`; `v0.1.0` follows
once the `pace-cnn` port below has run.

## What it does

- `validate` and `render` check a manifest and print it as the pipeline will use it, without
  reading data or loading a framework.
- The manifest names its columns as Ludwig does: one input feature per column, of type `number`,
  `category`, `binary` or `image`, and one output feature of type `category`, `binary`, `number` or
  `anomaly`
  (schema `caravan/v0.3`). Each type brings its preprocessing: fitted on the training
  part, built into the model, so a firmware passes raw values.
- `build`, `train`, `quantize` and `export` run the stages: the data stage splits the data and fits
  each feature's preprocessing on the training part, the model is built from a template (`mlp`,
  `conv1d`, `conv2d` or `autoencoder`) behind the features' own layers, checked against every target board's flash and RAM
  before any training, trained, converted to int8 and gated on what the conversion cost — accuracy
  for a class, the mean absolute error for a number — then exported with an operator resolver, one
  runner skeleton per board and an interface contract that names every input with its position,
  element type, shape and what was fitted for it.
- Every stage is cached by what it reads, so a change re-runs only what it affects.
- A dataset can name its own split per record (`preprocessing.split: {type: fixed, column: ...}`),
  so subjects, vehicles or sessions stay on one side of it.
- Windows know their recordings: a window never spans two data files, and windowed data is split by
  recording, by a group column or in contiguous blocks, so no test window has its training
  neighbour beside it.
- The training framework's output is kept in `framework.log` in the run directory, not on the
  console.

## Where it runs

| Part | Python | Install |
|---|---|---|
| core: `validate`, `render`, `templates`, `boards` | 3.13, 3.14, 3.15 | the wheel, no extras |
| reading and running exported models (`verify` extra) | 3.13, 3.14 | `[verify]` |
| building, training, converting (`train` extra) | 3.13 | `[train,verify]` |

Linux and macOS. Installed from the GitHub release of the tag; not on the package index.

**The fifth candidate.** `v0.1.0rc5` makes windows know their recordings (manifest
`caravan/v0.3`, a breaking change; see the change notes below):
- a window never spans two data files, or two runs of a {mf}`preprocessing.recording_column`;
  each recording starts its own grid of windows;
- with a window and no stated split, the data stage splits by recording when three or more
  recordings yield windows, and in contiguous blocks otherwise, and records which it chose. The new
  types `recording`, `group` and `blocked` can be stated too. On the review's example, a random
  split left 13 of 15 test windows beside a training window; the new default leaves none;
- {mf}`preprocessing.window_stride` lets windows overlap, with every row kept in one part;
- {mf}`preprocessing.window_label` says which label a window takes: `last` (the default for a
  `number` output, which used to lose every window), `mean`, `majority`, `all_equal`, or
  `{any: <value>}` for short bursts;
- the run report names the recordings, the windows dropped and why, and which recording or block
  went to which part; the interface contract is version 4 (`training_stride`, `window_label`).

**The fourth candidate.** `v0.1.0rc4` adds:
- the templates for the application classes: `conv2d`, a convolution over a plane, and
  `autoencoder`, anomaly detection from normal data; the `image` input type and the `anomaly`
  output, with its budget `auc_drop_max`. The manifest stays `caravan/v0.2`: these are additions;
- the documentation organised like Django's: a contents page, the tutorial in four parts, topic
  guides, a reference with one entry per field, command, rule and board, how-to guides and a
  glossary. Every earlier address forwards to its new page.

**The third candidate.** `v0.1.0rc3` carried the documentation site, test windows in the export,
and the part of the tutorial that runs an exported model on a generic ESP32 and checks its answers
against the host's.

Its firmware is built for the ESP32 before the release is published. What it establishes on a
board is what the owner's board run records ([board runs](../ref/board-runs/index.md)). Until then the
[compatibility page](../ref/compatibility.md) states the ESP32 as built, not run. A defect the board run
finds is fixed in a later candidate.

## Known limits

- Training and conversion need Python 3.13: TensorFlow publishes no stable wheel for anything
  newer (2.22.0rc0 is still a candidate, checked 2026-10-23).
- `export` needs the training extra even when training and quantization are cached; a machine with
  only the runtime cannot export a model trained elsewhere.
- Memory and flash figures are lower bounds computed from the model, not measurements on a board.
- One output per model. Input types are `number`, `category`, `binary` and `image`; text,
  sequences and audio have no path to the device in this release. An image is the model's only
  input.
- The typed example is larger than an untyped one would be: 27,608 bytes for the pilot, against
  14,856 for the same model reading one int8 tensor of all columns. The category
  column now carries information it did not before — a CAN identifier was a meaningless magnitude
  — and its embedding costs the difference.
- Windows overlap only when the manifest asks for it (`window_stride`), and only with a split that
  keeps every recording, group or block on one side.

## Change notes

Three breaking manifest changes since development began, each with the edit an author makes by hand
in [the change notes](../ref/manifest-changes.md): `caravan/v0` → `caravan/v0.1`, and `caravan/v0.1` →
`caravan/v0.2` (typed features in Ludwig's names), and `caravan/v0.2` → `caravan/v0.3` (windows
that know their recordings, a new default split). `v0.1.0rc1` read `caravan/v0.1`, `v0.1.0rc2` to
`v0.1.0rc4` read `caravan/v0.2`, and `v0.1.0rc5` reads `caravan/v0.3`. Before 1.0.0 nothing is migrated; a manifest in another form is refused with the
version this build reads.

### `caravan init`: one proposal

Not a manifest change, but the command line changed. `caravan init` shows one proposal and asks only
the boards and what it is unsure of. `--yes` accepts the proposals; `--no-input` now only means
"never ask" and writes nothing without `--yes` — a script that used `--no-input` to accept adds
`--yes`. Without a terminal, `init` never asks. `--plain` and the `authoring` extra are gone: the line
mode is the only interface, and an install that names `authoring` gets the default installation.
New: `--json`, `--agents-md`.
