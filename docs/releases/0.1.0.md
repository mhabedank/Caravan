# Caravan 0.1.0

The first release: a declarative pipeline from one YAML manifest to an int8 model, its C array and
its interface contract, for microcontrollers. Candidates are tagged `v0.1.0rcN`; `v0.1.0` follows
once the `pace-cnn` port below has run.

## What it does

- `validate` and `render` check a manifest and print it as the pipeline will use it, without
  reading data or loading a framework.
- The manifest names its columns as Ludwig does: one input feature per column, of type `number`,
  `category` or `binary`, and one output feature of type `category`, `binary` or `number`
  (schema `caravan/v0.2`). Each type brings its preprocessing: fitted on the training
  part, built into the model, so a firmware passes raw values.
- `build`, `train`, `quantize` and `export` run the stages: the data stage splits the data and fits
  each feature's preprocessing on the training part, the model is built from a template (`mlp` or
  `conv1d`) behind the features' own layers, checked against every target board's flash and RAM
  before any training, trained, converted to int8 and gated on what the conversion cost — accuracy
  for a class, the mean absolute error for a number — then exported with an operator resolver, one
  runner skeleton per board and an interface contract that names every input with its position,
  element type, shape and what was fitted for it.
- Every stage is cached by what it reads, so a change re-runs only what it affects.
- A dataset can name its own split per record (`preprocessing.split: {type: fixed, column: ...}`),
  so subjects, vehicles or sessions stay on one side of it.
- The training framework's output is kept in `framework.log` in the run directory, not on the
  console.

## Where it runs

| Part | Python | Install |
|---|---|---|
| core: `validate`, `render`, `templates`, `boards` | 3.13, 3.14, 3.15 | the wheel, no extras |
| reading and running exported models (`verify` extra) | 3.13, 3.14 | `[verify]` |
| building, training, converting (`train` extra) | 3.13 | `[train,verify]` |

Linux and macOS. Installed from the GitHub release of the tag; not on the package index.

**The third candidate.** `v0.1.0rc3` carries three things:
- the documentation site;
- test windows in the export;
- the route's leg that runs an exported model on a generic ESP32 and checks its answers against
  the host's.

Its firmware is built for the ESP32 before the release is published. What it establishes on a
board is what the owner's board run records ([board runs](../board-runs/index.md)). Until then the
[compatibility page](../compatibility.md) states the ESP32 as built, not run. A defect the board run
finds is fixed in a later candidate.

## Known limits

- Training and conversion need Python 3.13: TensorFlow publishes no stable wheel for anything
  newer (2.22.0rc0 is still a candidate, checked 2026-10-23).
- `export` needs the training extra even when training and quantization are cached; a machine with
  only the runtime cannot export a model trained elsewhere.
- Memory and flash figures are lower bounds computed from the model, not measurements on a board.
- One output per model. Input types are `number`, `category` and `binary`; text, sequences,
  images and audio have no path to the device in this release.
- The typed example is larger than an untyped one would be: 27,608 bytes for the pilot, against
  14,856 for the same model reading one int8 tensor of all columns. The category
  column now carries information it did not before — a CAN identifier was a meaningless magnitude
  — and its embedding costs the difference.
- Windows never overlap.

## Change notes

Two breaking manifest changes since development began, each with the edit an author makes by hand
in [the change notes](../manifest-changes.md): `caravan/v0` → `caravan/v0.1`, and `caravan/v0.1` →
`caravan/v0.2` (typed features in Ludwig's names; `v0.1.0rc1` read `caravan/v0.1`,
`v0.1.0rc2` and `v0.1.0rc3` read `caravan/v0.2`). Before 1.0.0 nothing is migrated; a manifest in another form is refused with the
version this build reads.

## Release gate

The constitution's gate before a framework release, and where each item was shown:

- semantic versioning: `0.1.0rc1`, `0.1.0rc2`, `0.1.0rc3`, PEP 440;
- a change note for every breaking schema change: see above;
- the pilot manifest green end to end: the `release.yml` run of the tag (linked when the release is
  made).
